# 隙间（XiJian）保姆级维护教程

> 适用范围：Core API、DevKit、资源包系统（§B）、版本号、存储迁移。
> 本文档面向两类人：**项目维护者**（预置资源包、改版本号、改文档）和
> **内容开发者**（用 DevKit 做角色/世界并打包发布）。
>
> 2026-08-04 建立。macOS 路径以 `~/Library/Application Support/XiJian/` 为例；
> Windows/Linux 同理替换（路径规则见 §3）。

---

## 0. 三句话总览

1. **所有持久化数据**都存 `~/Library/Application Support/XiJian/Core/`（简称 **CORE_ROOT**），旧 `~/.xijian` 会在启动时自动迁移。
2. **资源包 = 固实 7z（或 zip）归档**，里面是 `manifest.json` + `characters/`、`worlds/`、`memories/` 目录。DevKit 导出即包，Core 安装即用。
3. **版本号只改一个文件**：`Config/Config.json`，然后跑一条命令同步到全仓库。

## 3. 存储布局与旧数据迁移

### 3.1 统一存储根（CORE_ROOT）

**一切持久化文件**都存这里，由 `Config/Config.json` 无关，由 core 配置决定：

```
~/Library/Application Support/XiJian/Core/
├── xijian.db              # SQLite 数据库
├── files/                 # 用户上传/导入的文件（含导入的归档）
├── models/                # 模型权重
├── snapshots/             # 快照
├── audit/                 # 审计日志
├── packs/                 # 【资源包】已安装的包，每包一个子目录（§4）
├── logs/                  # 日志
└── run/                   # 运行时文件（token 等）
```

- 覆盖整个存储根的**环境变量**：`XIJIAN_DATA_DIR`（优先级最高，测试和高级用户用它整体搬迁）。
- core 的 `config.toml` `[storage]` 段可分别改子目录名；`base_dir` 默认就是 CORE_ROOT。
- core 的 `config.toml` `[snapshots]` 段（A5.3）：`compression_backend`（zstd|zlib|auto，默认 auto，AC-3 用 zstd）与 `max_single_snapshot_bytes`（单快照上限，缺省 500 MiB）可选；也可运行时 `PUT /v1/xijian/backups/policy` 调整。
- DevKit 的工作目录（`DevKit/`）**不属于** Core 存储，是编辑器自己的保存目录；Core 通过目录桥接读取它。

### 3.2 旧数据自动迁移（`~/.xijian` → CORE_ROOT）

升级到新版本后首次启动，Core 自动把 `~/.xijian` 下的数据迁移过来：

- 迁移**幂等**：完成后在 CORE_ROOT 写 `.migrated_from_xijian` 标记，再次启动直接跳过。
- 迁移**非破坏**：旧目录永不删除。
- 迁移**冲突感知**：目标已有同名且内容不同的文件时，**不覆盖**，记入冲突清单。

冲突处理 API：

```bash
# 查看迁移状态与冲突
curl -H "Authorization: Bearer <token>" http://127.0.0.1:18500/v1/xijian/migration/status
curl -H "Authorization: Bearer <token>" http://127.0.0.1:18500/v1/xijian/migration/conflicts

# 解决冲突：keep="legacy"（保留旧 ~/.xijian 版本）或 keep="new"（保留新位置版本）
curl -X POST -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"conflict_id": "<id>", "keep": "legacy"}' \
  http://127.0.0.1:18500/v1/xijian/migration/resolve
```

> 客户端（macapp 等）应当在启动后检查 `/v1/xijian/migration/status`，
> 若有未解决冲突，向用户展示两个文件的差异（大小/修改时间/路径），让用户选择保留哪个。

## 4. 资源包系统（§B）—— 核心流程

### 4.1 包格式（契约）

一个资源包归档（7z 固实 或 zip）的根级布局：

```
manifest.json                     # 必需：包清单
characters/<id>/character.json    # 角色（kind=character 时必需）
characters/<id>/persona.md        # 可选：角色人设
memories/<id>/entries.json        # 可选：角色的初始记忆条目
worlds/<id>/world.json            # 世界（kind=world 时必需）
worlds/<id>/world_doc.md          # 可选：世界文档
worlds/<id>/world_config.json     # 可选：结构化世界配置（时间/天气等）
audio/**  model/**  motion/**     # 可选：素材资源（保留不解析）
```

`manifest.json` 示例：

```json
{
  "schema": "xijian.pack/v1",
  "package_id": "char-yuki",
  "name": "Yuki",
  "version": "1.0.0",
  "kind": "character",
  "author": "The XiJian Development Group",
  "description": "内置角色：Yuki",
  "dependencies": []
}
```

字段规则：

| 字段 | 必填 | 说明 |
|------|------|------|
| `schema` | 是 | `xijian.pack/v1`；`xijian.devkit.submission/v1` 也兼容（DevKit 提交归档） |
| `name` | 是 | 显示名 |
| `version` | 是 | 版本号字符串 |
| `kind` | 是 | `character` / `world` / `mixed` |
| `package_id` | 否 | 小写字母数字 + `._-`；缺省由 `name` 派生 |
| `author` / `description` / `dependencies` | 否 | 元信息；`dependencies` 为依赖的 package_id 列表（暂不强制校验） |

### 4.2 用户怎么安装包（三种方式）

**方式 A：拖进目录（最省事）**

1. 下载 `.7z` 或 `.zip` 资源包。
2. 把归档**直接**放进 `~/Library/Application Support/XiJian/Core/packs/`（或先解压成目录放进去）。
3. 调用 `POST /v1/xijian/packs/rescan`（或重启 Core），包即被扫描、校验并加载。

**方式 B：API 上传**

```bash
# multipart 文件上传
curl -X POST -H "Authorization: Bearer <token>" \
  -F "file=@/path/to/pack.7z" \
  http://127.0.0.1:18500/v1/xijian/packs/install

# 或给服务端本地路径（适合已落盘的归档）
curl -X POST -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"path": "/path/to/pack.7z"}' \
  http://127.0.0.1:18500/v1/xijian/packs/install
```

**方式 C：异步导入（旧接口，保持兼容）**

```bash
# 1) 先上传归档到文件存储，拿到 file_id
# 2) 发起导入
curl -X POST -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"name": "Yuki", "kind": "character", "file_id": "<file_id>"}' \
  http://127.0.0.1:18500/v1/xijian/resources/import
# 3) 轮询任务
curl -H "Authorization: Bearer <token>" http://127.0.0.1:18500/v1/xijian/resources/imports/<job_id>
```

### 4.3 查询与卸载

```bash
# 列出全部已安装包
curl -H "Authorization: Bearer <token>" http://127.0.0.1:18500/v1/xijian/packs

# 单个包详情
curl -H "Authorization: Bearer <token>" http://127.0.0.1:18500/v1/xijian/packs/<package_id>

# 卸载（移除运行时记录 + 删除包目录）
curl -X DELETE -H "Authorization: Bearer <token>" \
  http://127.0.0.1:18500/v1/xijian/packs/<package_id>
```

### 4.4 开发者怎么做包（DevKit 导出即包）

用 DevKit 编辑完角色/世界后，导出功能直接产出**合法资源包**：

- 角色导出 → `characters/<id>/character.json` + `persona.md`（+ `memories/<id>/entries.json`）
- 世界导出 → `worlds/<id>/world.json` + `world_doc.md` + `world_config.json`
- 归档根级自动写入 `manifest.json`（schema 为 `xijian.devkit.submission/v1`，Core 兼容接受）

即：**DevKit 导出 → 固实 7z → 用户用 §4.2 任意方式安装**。不需要手工拼包。
手动拼包的规范见 §4.1；包名/版本/作者等元信息通过 `build_manifest()` 的
`payload.name` / `Config.json Version.DevKit` 自动带上。

### 4.5 项目组/开发者怎么预置包

预置 = 随 Core 分发、首次启动自动安装的包。搜索顺序：

1. 环境变量 `XIJIAN_PRELOAD_PACKS_DIR` 指向的目录；
2. 冻结（PyInstaller）模式：可执行文件旁的 `preload_packs/`；
3. 源码开发模式：`core/preload_packs/`。

操作步骤：

1. 在 `core/preload_packs/` 放入 `.7z`/`.zip` 归档（或已解压的包目录）。
2. 启动 Core：`ensure_preload_packs()` 会**幂等**安装（同 package_id 且版本相同则跳过）。
3. 想给用户分发时，把该目录一并打进构建产物（构建脚本加一步）。

> macapp 侧的资源预置：macapp 已恢复维护；如需预置，在应用资源里放
> `preload_packs/` 并在首次启动时调 Core 安装接口即可，规则同上。

### 4.6 包引擎的安全与行为细节

- 支持 7z（py7zr，固实）与 zip（标准库）双格式；其他扩展名拒绝。
- **路径穿越防护**：归档内条目若含 `..`、绝对路径、Windows 盘符等，直接拒绝并清理半成品。
- manifest 缺失/非法/字段不合规 → 安装失败，报 `PackValidationError`。
- 安装即加载：角色进 `state.characters`（标记 `_pack_source`/`_pack_id`），世界进 `state.worlds` 并初始化环境/计算配置、按需生成 5 个基础 NPC（与 DevKit 预览行为一致）。
- 同 package_id 重复安装 = 覆盖（先卸后装），幂等。
- 卸载 = 清除该包全部运行时记录 + 删除包目录 + 移出索引。

## 5. 版本号维护（唯一事实源：Config/Config.json）

### 5.1 改哪里

只改 `Config/Config.json` 的 `Version` 段：

```json
"Version": {
  "Main": "v0.0.1-Beta",      // 项目整体版本
  "CoreApi": "v1.2.0-Alpha",  // Core 服务版本
  "DevKit": "v1.6.2",         // 开发者工具版本
  "macOSUIApp": "Unavailable" // macapp 已恢复维护；版本暂未接入同步脚本（见 §5.3）
}
```

### 5.2 怎么同步

```bash
# 预览将改哪些文件（不写入）
/opt/anaconda3/envs/xijianBase/bin/python core/scripts/sync-versions.py --dry-run

# 执行同步
/opt/anaconda3/envs/xijianBase/bin/python core/scripts/sync-versions.py

# CI 校验（任何目标不同步则退出码 1）
/opt/anaconda3/envs/xijianBase/bin/python core/scripts/sync-versions.py --check
```

同步映射：

| 目标文件 | 取哪个版本 | 变换 |
|----------|-----------|------|
| `core/pyproject.toml` `version` | CoreApi | PEP 440（`v1.2.0-Alpha` → `1.2.0a0`） |
| `core/xijian_api/__init__.py` `__version__` | CoreApi | 同上 |
| `core/xijian_api/_version.py`（生成） | CoreApi | 原始串 + PEP 440 双份 |
| `devkit/version.py` `FALLBACK_VERSION` | DevKit | 原始串（保留 `v` 前缀） |
| `devkit/xijian-devkit.spec` `CFBundle*` | DevKit | 仅数字段（`v1.6.2` → `1.6.2`） |

运行时的读取：

- Core 的 `GET /` 与 `GET /v1` 返回的 `server_version` 来自 `core/xijian_api/_version.py`（即同步后的 CoreApi）。
- DevKit 运行时版本来自 `devkit/version.py` 的 `get_app_version()`（读 Config.json，FALLBACK 兜底）。

### 5.3 刻意不动的

| 位置 | 原因 |
|------|------|
| `docs/api.md` 的 `api_version=1.0.0` | 这是 **API 协议版本**（兼容性契约），不是构建版本 |
| `macapp/*` 的 Info.plist | macapp 已恢复维护，但版本**尚未接入** sync-versions.py；接入后再同步 |
| `.github/workflows/*` | 构建流程不读版本号；如需 tag 过滤，另行处理 |

| 模块 | 测试文件 | 覆盖点 |
|------|---------|--------|

## 8. 文档同步规则

**任何行为变更，必须同步修改所有描述该行为的文档**。当前文档地图：

| 文档 | 内容 | 变更时必查 |
|------|------|-----------|
| `docs/api.md` | 全量 API 契约（§3.8 资源与导入 = 资源包） | 改端点/入参/响应时 |
| `docs/CoreStartupGuide.md` | 启动流程、横幅、存储根 | 改启动行为/路径时 |
| `docs/BuildGuide.md` | 打包模式 vs 开发模式对照表 | 改存储/构建行为时 |
| `docs/notes.md` | 开发日志（每个章节改动当日追加一条） | **每次**改完功能 |
| `docs/Dev. Function List功能清单v2.md` | 功能清单与版本表 | 落地新功能时 |
| `docs/Dev.md` | 开发者工具指南 | 改 DevKit 行为时 |
| `docs/macapp.md` | macOS 客户端（构建/运行/功能范围） | 改 macapp 行为/结构时 |
| 本文档 | 维护教程 | 流程/规则变化时 |

### 常见陷阱

1. **只改了代码没改文档** → 违反规则 12；提交前 grep 旧关键词（如 `~/.xijian`、`resources/import`）。
2. **只改了一个文档** → 多个文档描述同一行为时必须全部改（用上面地图核对）。
3. **在 UI 里写开发注记** → 禁止；任何面向用户的文案保持干净。
4. **用了 `python3`/`pip3`** → 必须用 `/opt/anaconda3/envs/xijianBase/bin/python`（或 base 的 `/opt/anaconda3/bin/python`），系统 Python 有已知 bug。
5. **`rm -rf` 删除文件** → 禁止；用 `trash` 或 Finder 移到废纸篓。应用代码内部对受管数据目录的正常清理（如卸载包）除外。

## 9. 常见问题排查（FAQ）

| 症状 | 排查 |
|------|------|
| 启动横幅显示存储根还是 `~/.xijian` | 用了旧版配置缓存；检查 `core/config.toml` 的 `[storage] base_dir` 与 `XIJIAN_DATA_DIR` |
| 装了包但角色不出现 | 调 `POST /v1/xijian/packs/rescan`；确认归档是 §4.1 布局且 manifest 合法 |
| 安装报 `PackValidationError` | 用 `unzip -l pack.zip` / 7z 工具查看归档结构；重点看 `manifest.json` 的 schema/name/version/kind |
| 7z 装不了 | 确认 py7zr 已装（`pip show py7zr`）；py7zr 在核心依赖，正常装 core 即有 |
| 迁移状态有冲突 | `GET /v1/xijian/migration/conflicts` 看差异，`POST resolve` 选保留方 |
| `server_version` 和 Config.json 对不上 | 跑 `sync-versions.py`；确认 `core/xijian_api/_version.py` 已更新 |
| 测试写了真实用户目录 | 违反隔离铁律；packs/migration 必须 `_set_paths_for_test` |
