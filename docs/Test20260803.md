## 1. 背景与思路

> 一个测试工程师走进一家酒吧，要了一杯啤酒；
> 一个测试工程师走进一家酒吧，要了 0.7 杯啤酒；
> 一个测试工程师走进一家酒吧，要了 -1 杯啤酒；
> 一个测试工程师走进一家酒吧，要了 2^32 杯啤酒；
> 一个测试工程师走进一家酒吧，要了一杯洗脚水；
> 一个测试工程师走进一家酒吧，要了 NaN 杯 Null；
> 一个测试工程师走进一家酒吧，要了一杯啤酒';DROP TABLE 酒吧；
> ……然后一名顾客点了一份炒饭，酒吧炸了。

用户把这段笑话当作需求：**程序必须足够强大，才能与用户抗衡**。对 Core 来说，「酒吧不炸」的判据是：

1. 正常请求照常工作（200）；
2. 恶意/畸形/边界输入得到**干净的 4xx**（`invalid_request_error`），绝不 500、不崩溃；
3. 非法状态转换、越权、注入、并发竞争不产生脏数据、不损坏存储；
4. 所有滥用结束后，系统仍然健康（`/healthz` 200、正常请求可用）——「点炒饭不会炸」。

### 3.3 已确认安全（无需修复）

- **SQL 注入**：`store.py` 全部使用参数化查询（`?` 占位符），表名来自固定 bucket 名。实测 `'; DROP TABLE store_characters;--` 作 ID → 404，表数据完好（18 类测试验证）。
- **路径穿越**：`../`、`%2e%2e`、`%00` 空字节作 ID → 404/400，无文件系统越界。
- **认证**：`/healthz` 之外所有端点强制 Bearer；错 token/伪装 scheme/大小写变体均 401。
- **NaN 金额**（钱包层）：`_validate_amount` 用 `math.isfinite` 拒绝 NaN/Inf → 400（虽 `_parse_positive_number` 未显式拒绝，但被 stub 兜底）。

## 4. 各场景详细结果

19 类全部通过，抽查要点：

- **3（小数）**：`amount=0.7` 正常入账并四舍五入到 6 位小数；分页 `limit=0.7` 安全钳制。
- **4（负数）**：负金额 → 400，钱包余额不变，无脏记录。
- **5（大数）**：`2^32`、`2^63` 金额 → 400（超出合理范围被拒）；`1e308` 不溢出崩溃。
- **7（类型混淆）**：`bool` 当数字（`top_k=True`、`temperature=true`）→ 400（bool 是 int 子类，特意显式拒绝）；数字字符串 `"0.7"` 按原语义解析。
- **10（幂等）**：同 key 同 body 重放返回缓存响应 + `Idempotency-Replayed: true`；同 key 不同 body → 409 `idempotency_key_conflict`。
- **11（状态机）**：`DELETE` 不存在角色 → 404；重复 `DELETE` → 204 → 404 精确；删后 GET → 404，不崩溃。
- **12（乱码）**：`b'\xff\xfe'` 等无效 UTF-8 body → 400/413，不 500；mojibake 字符串安全存储。
- **13（NaN/Null）**：chat 数值、钱包金额、`min_score` 的 NaN/±Inf → **400**（QA 后由「不 500」强化为钉死 400）；null → 走默认值或 400。
- **14（超大）**：500 层深嵌套、1MB 字符串、混合类型数组 → 200 或 400，不栈溢出不 500。
- **16（越权）**：无 token → 401；错 token → 401；`Basic` scheme → 401；`bearer` 小写 → 401；`/healthz` 无论有无 token 都 200。
- **17（并发）**：5 线程 × 4 次并发存款后余额精确等于 20.0（锁有效）；并发转账同样精确（Q3 修复后）。
- **19（事后回归）**：全部滥用后 `/healthz` 200、聊天 200、写入 201、各 store 表数据完好。

## 7. 结论

**Core 现在能接住「测试工程师进酒吧」的全部 19 类场景**：正常请求照常、恶意输入干净 4xx、并发不丢数据、注入无效、滥用后系统依旧健康——最后一位顾客的炒饭，酒吧没有炸。

- 新增 121 条对抗性测试，覆盖 19 类滥用 + 9 条 QA 回归；
- 修复 3 大类 14 处真实缺陷（含 1 个并发丢更新、2 个高危 500、1 个响应头注入）；
- 全量 2124 passed / 46.92s，0 回归；
- 所有修复仅涉及 `core/xijian_api/` 输入校验层与钱包锁，未改变正常路径语义。

**遗留（已知、有意保留）**：

- `xijian_economy._parse_positive_number` 未显式拒绝 NaN/Inf，但被钱包 stub 兜底为 400——若未来 stub 被替换需同步此约束；
- 部分 OpenAI 兼容端点（如 embeddings）在无后端环境返回 503 `backend_unavailable`，属环境性预期，非健壮性缺陷；
- Core 仍为进程内 + SQLite 内存缓存架构，`MAX_CONTENT_LENGTH` 未显式配置（Flask 默认不限）——超大 body 由 JSON 解析层钳制，生产部署如需硬上限建议在反向代理层配置。
